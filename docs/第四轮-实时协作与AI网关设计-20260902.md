# 第四轮：实时协作一步到位 + 编辑能力盘点 + AI 网关设计（2026-09-02）

这轮是方案讨论，未写代码。三个议题：①锁+共享混合模式怎么做、费不费资源；②现在编辑能力对标 PS 到什么程度；③用 OpenAI 兼容 API 替代本地模型。

## 一、"默认上锁 + 点击共享" 混合模式（推荐这么做）

### 先回答你的问题：会不会更耗费资源？

**不会，恰好相反——这是最省资源的设计。**

| 模式 | 流量本质 | 成本 |
| --- | --- | --- |
| 上锁（默认） | 只有 10 秒一次的锁状态轮询（几十字节） | **≈ 0**，相当于现在 |
| 共享（点击后） | 房间内广播操作增量 | 只在有人围观时才产生 |
| 全时共享 | 人人都在房间里，即使没人看也在广播 | 恒定开销，浪费 |

锁是**免费的**，共享是**按需付费**的。默认锁 + 点击共享 = 把"付费"的时机交给用户决定，比全时共享省，比纯锁多了协作能力。这也是 Figma（默认私有，点 Share 才邀请）和 Google Docs 的共同做法。

### 一步到位的技术选型

**关键决策：涂改层（P图）不同步像素，同步"矢量笔画操作"。**

| 方案 | 一笔的流量 | 9 个观众 × 6 笔/秒 | 评价 |
| --- | --- | --- | --- |
| 同步光栅（dirty-rect PNG） | 20~60KB | 1~5 Mbps | 5M 带宽顶满，还要处理压缩/丢帧 |
| **同步笔画向量**（Figma/Excalidraw 的做法） | 0.2~2KB | **~12KB/s = 0.1Mbps** | 观众本地重放笔画，画质无损、可撤销、可回放 |

一笔画 = `{opId, tool, color, size, points[], author}`。观众收到后在本地 canvas 重放这一笔；撤销 = 撤销操作日志；断线重连 = 服务端重放全量日志。**这样"多人实时 P 图"就从带宽怪兽变成了白菜价。**

具体栈（都是成熟件，不造轮子）：

```
浏览器 A/B/C ──WebSocket──> y-websocket 服务（新进程，:3001）
                              │  Yjs Doc: annotations + textLayers + paintOps
                              │  每房间一个 Doc，内存几十 KB
                              └──debounce 落库──> SQLite（现有表结构不变）

标注/标号/文字层  → Yjs Map/Array（真多人同时编辑，自动合并，无冲突）
涂改层            → Yjs Array<PaintOp>（矢量笔画日志，观众重放）
锁与共享          → 房间元数据（谁持有锁、共享是否开启、谁被授权画笔）
```

### 产品流程（按你描述的交互）

1. 点开一张图进入编辑 → **自动上锁**（你是锁持有者），别人进来看到"🔒 XX 正在编辑"和**修改前**的画面
2. 你点 **「共享编辑」** → 房间开启广播，其他人画面实时跟随
3. 观众默认**只能看**；你点他头像授予「可画」→ 他才能下笔（这是防止"人人都能画"把图改烂的安全阀，也正是你说的"又有多人修改能力又有上锁能力"）
4. 你关页/点「结束共享」→ 广播停止，锁释放；期间所有改动已落库，别人再进来看到的是**修改后**
5. 冲突兜底：即使全走实时，保存时仍校验版本，避免老版本覆盖新版本

### 资源账（按你定的上限：3 房间 × 2 操作 + 3 观看 = 15 连接）

| 项 | 估算 |
| --- | --- |
| Yjs 标注增量 | 6 操作者 × 2 ops/s × ~300B ≈ **4KB/s** |
| 笔画向量 | 6 × 2 笔/s × 1KB ≈ **12KB/s** |
| 合计 | **<50KB/s ≈ 0.4Mbps**，5M 带宽占用不到 10% |
| 服务器 CPU | Yjs 编码 + fanout，2C 空闲档 |
| 内存 | 每房间 Doc 几十 KB，3 房间可忽略 |
| **结论** | **现配置直接跑 L3，不需要加钱** |

唯一建议花的钱：带宽从 5M 提到 **10M**（约 +¥50/月）——不是为了现在的 15 人，而是给"以后 10 人围观一张图 + 上传导出并发"留余量。不提也能跑。

### 实施量
| 阶段 | 内容 | 工期 |
| --- | --- | --- |
| L1 | 编辑锁 + 轮询（不用 WebSocket，立刻解决互相覆盖） | 1~2 天 |
| L2 | y-websocket 服务 + 标注/文字层实时 | 3~5 天 |
| L3 | 涂改层笔画日志 + 观看重放 + 授权画笔 | 4~6 天 |
| 合计 | | **约 2 周** |

## 二、图片编辑能力现在到什么水平？对标 PS 多少？

诚实盘点。PS 的功能面（工具栏+菜单+面板）大约 **70+ 个功能点**；我们目前有 **~18 个**。两个口径：

- **功能覆盖面**：约 **20~25%**——我们不是通用修图软件，这个数字低是设计使然
- **漫画汉化关键路径覆盖率**：约 **80%**——标号→录入→审校→涂白→嵌字→导出，主干已经闭环

### 已具备（对标 PS 对应功能）
| 我们 | PS 对应 | 状态 |
| --- | --- | --- |
| 画笔/橡皮（可调大小、任意颜色） | 画笔/橡皮 | ✅ |
| 吸管 | 吸管 | ✅ |
| 矩形/套索填充 | 选区+填充 | ✅（无羽化/抗锯齿） |
| 仿制图章（Alt 取源） | 仿制图章 | ✅（无对齐模式/压力） |
| 文字层（字号/颜色/描边/对齐/粗细） | 文字工具 | ⚠️ 缺竖排/字体/字距/行距 |
| 背景锁定 + 涂改层 + 文字层分层 | 图层 | ⚠️ 只有 2 层半，无逐层管理 |
| 撤销/重做（50 步） | 历史记录 | ⚠️ 步数少、无快照 |
| 缩放/平移/适应窗口 | 缩放工具 | ✅ |
| 内容感知填充（去字） | 内容识别填充 | ✅ telea 级（无 LaMa 质量） |
| 标注/标号/审校/LabelPlus 互通 | 无（PS 靠脚本） | ✅ **PS 没有，这是我们的长板** |
| 嵌字草稿/导出/写回空间 | 存档 | ✅ |
| OCR 自动标号 | 无 | ✅ |
| 空间/导出/多人权限 | 无 | ✅ |

### 缺失清单（按汉化需求排序，前 5 个最值）
1. **文字层逐层管理**（列表选中/隐藏/排序/改层级顺序）——已可拖拽，还差面板
2. **竖排文字**（日漫刚需）
3. **选区进阶**：羽化、加/减选区、魔棒（按颜色选气泡）
4. **仿制图章的"对齐"模式** + 笔刷不透明度/硬度
5. **变换**：选中区域旋转/缩放/斜切（贴字对位用）
6. 滤镜：高斯模糊（做景深/马赛克）、锐化
7. 渐变工具、油漆桶（连续填充）
8. 路径/钢笔（精确气泡描边）
9. 无限历史 + 快照
10. 图层不透明度/混合模式

### 结论
当前定位是"**专注汉化的协作工具**"：PS 覆盖面我们只有 1/4，但汉化主干 80% 已闭环，且有多人协作、LabelPlus 互通、OCR 这三块 PS 没有的东西。参照物应该是 **Photopea**（网页版 PS，功能≈全量 PS 但无协作、无汉化工作流）——我们短期内不去拼功能广度，拼"汉化团队用得顺"。

## 三、AI 能力：BYO Token 的 OpenAI 兼容网关（可行，且比本地部署更合适）

你说的方向成立，两个任务分开看：

### 3.1 OCR（识图→标号提案）：完全可行 ✅

DeepSeek 确实上了视觉 API：`deepseek-v4-flash-vision`（2026-08-21 上线官方首个看图 API），**和文本共用同一端点** `https://api.deepseek.com/v1/chat/completions`，请求体里给图片即可。这就是标准的 OpenAI 兼容形态，我们可以做成通用适配：

```
设置页（创作者填）：
  Base URL   https://api.deepseek.com/v1   （或任何 OpenAI 兼容网关）
  API Key    sk-****                       （只显示尾 4 位）
  模型       deepseek-v4-flash-vision      （或 gpt-4o-mini / glm-4v / qwen-vl…）

OCR 流程：图片缩到 ~1600px → base64 image_url
  prompt: 找出图中所有对话气泡/文字块，输出 JSON
          [{x,y,w,h,source_text}]（归一化 0~1）
  → 返回 proposals → 走现有「勾选采纳」流程（不自动写库，和现在一致）
```

- 成本：视觉模型通常 **¥0.001~0.01/图** 级别（以官方价格页为准），一话 200 图也就几块钱
- 兼容性：任何 OpenAI 兼容 + 支持图片输入的模型都能插（DeepSeek/GPT/GLM/Qwen/豆包…）
- 额外收益：VLM 会"看图说话"，可以顺带产出气泡的角色/情绪/是否拟声词这类元数据，给分组和样式预设用

### 3.2 去字（LaMa 替代）：可行但有坑 ⚠️

OpenAI 兼容的图像编辑是 `POST /v1/images/edits`（image + mask + prompt），gpt-image 系列（1/1.5/2）和国内一批兼容网关都支持。**但有个必须知道的差异**：

> **生成式编辑 ≠ LaMa 的内容感知填充。** GPT-Image 的 mask 编辑本质是"重新生成"，社区反馈 mask 外的像素可能被重绘、线稿可能漂移变形。而漫画去字要的恰恰是"只动 mask 内、气泡框一根线都不能变"。

所以我的建议是三档，让创作者自己选：

| 档位 | 引擎 | 成本 | 适用 |
| --- | --- | --- | --- |
| 默认 | **本地 telea**（现有，零依赖） | 0 | 快速涂白，确定性 100%，mask 外一个像素都不动 |
| 进阶 | **本地 LaMa**（模型仅 ~200MB，Docker 一个容器） | 0（电费） | 结构保持最好，真 LaMa 质量 |
| AI 档 | **/v1/images/edits**（用户自己的 key） | ~$0.02-0.19/图 | 需要理解内容时（如气泡里有图案） |

如果上 AI 档，必须加**漂移校验**：拿返回图与原图在 mask 外做像素 diff，差异超阈值就拒收并回退 telea，避免"AI 帮你把线稿画歪了"。此外保留一个"自定义 LaMa 端点"输入框——谁想自建就填个 URL，不强求 OpenAI 兼容。

### 3.3 Token 放哪、怎么管

| 方案 | 说明 | 建议 |
| --- | --- | --- |
| 服务器存 | `data/ai.json`（`data/` 已在 .gitignore） | ✅ **推荐**，全站共用一份，设置页管理 |
| 每用户存 | users 表加加密字段 | 备选，适合"各用各的额度" |
| 前端 localStorage | 永不落服务端 | 不推荐：换设备就丢，且没法做服务端降级 |

配套护栏：key 只显示尾 4 位、每图 token 预算、每空间每日上限、调用失败自动降级 telea、调用日志（谁花了多少）。互相认识的团队用"服务器存一份 + 任何登录用户可发起"最省心。

## 四、需要你拍板的 3 个点

1. **共享后的画笔权**：观众进来默认只能看、由你逐个授权"可画"（推荐），还是进房即可画？
2. **AI 去字的漂移风险**：能接受"可能把线稿画歪"就上 `/v1/images/edits`；不能接受就本地 LaMa（200MB，不花钱）为主、AI 为辅
3. **实施顺序确认**：我建议 **L1 锁 → L2 文本实时 → L3 笔画直播（合计约 2 周）**，AI 网关（2~3 天）可并行插在任意位置。如果你要"先见效"，就从 L1 + AI 网关开始，一周内能看到两个明显变化
