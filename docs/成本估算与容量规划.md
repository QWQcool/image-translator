> 汇率按 **1 USD ≈ 7.2 CNY** 估算。容量数字基于下述假设推算，请按你的实际预期调整。

## 二、容量测算

### 2.1 单张图片的体积（决定一切的前提）

原始推特图片平均约 600 KB。经过本项目的处理（统一转 WebP q82 + 最长边限制 1800 + 缩略图 520 宽 WebP）：

| 项目 | 平均体积 |
| --- | --- |
| 原图（转 WebP 后） | **≈ 220 KB** |
| 缩略图 | **≈ 35 KB** |

**实测数据**（2400×1600 高斯噪声图，信息熵接近真实照片，比纯色图有代表性）：

```
原始 JPEG  2249 KB  →  落盘 WebP 1800×1200  808 KB     减少 64.1%
```

> 这是整套方案里性价比最高的优化：**存储、流量、CDN 费用同时降 60% 以上，且对标注质量无影响**
> （1800px 足够看清图片上的文字，标注场景不需要 4K 原图）。

### 2.2 存储量（三档)

| 档位 | 人均图数 | 总图数 | 原图 | 缩略图 | **合计** |
| --- | --- | --- | --- | --- | --- |
| 轻量 | 50 张 | 5 万 | 11 GB | 1.8 GB | **13 GB** |
| **中等（按此规划）** | 200 张 | 20 万 | 44 GB | 7 GB | **51 GB** |
| 重度 | 500 张 | 50 万 | 110 GB | 18 GB | **128 GB** |

### 2.3 月流量

按日活 150 人（1000 用户的 15%）计：

- 缩略图浏览：150 人 × 120 张 × 35 KB × 30 天 ≈ **19 GB**
- 原图编辑：150 人 × 15 张 × 220 KB × 30 天 ≈ **15 GB**
- **下行合计 ≈ 34 GB/月**（上行约 8 GB，入流量通常免费）

**结论：流量不是瓶颈**。哪怕是入门级套餐的流量包都绰绰有余。
真正的瓶颈是**并发带宽**和**存储量**。

## 三、基础设施方案对比

### 方案 A：腾讯云国内（推荐 —— 用户群在国内时）

| 项目 | 规格 | 单价 | 月成本 |
| --- | --- | --- | --- |
| 轻量应用服务器 | 锐驰型 **4核8G / 200Mbps 峰值 / 无限流量** | ¥230/月 | ¥230 |
| 对象存储 COS | 标准存储 51 GB | ¥0.099/GB/月 | ¥5 |
| CDN 流量 | 34 GB | ≈ ¥0.2/GB | ¥7 |
| 域名 | .com | ¥60/年 | ¥5 |
| **合计** | | | **≈ ¥247/月** |

- 年付 85 折 → **≈ ¥213/月**
- 锐驰型是「200Mbps 峰值带宽 + 无限流量」，**直接绕开了国内带宽贵这个老问题**
- ⚠️ **国内服务器必须 ICP 备案**（免费，但要 10~20 天），域名也需已备案

### 方案 B：腾讯云海外 + Cloudflare R2（最便宜）

| 项目 | 规格 | 单价 | 月成本 |
| --- | --- | --- | --- |
| 轻量服务器（海外） | 入门型 4核8G / 30Mbps / 3584 GB 流量 | ¥215/月 | ¥215 |
| R2 存储 | 51 GB − 10 GB 免费额度 = 41 GB | $0.015/GB/月 | ≈ ¥4.5 |
| R2 操作 | Class A 写 100 万次 / Class B 读 1000 万次 免费 | | ¥0 |
| **R2 出流量** | **永久免费** | | **¥0** |
| 域名 | Cloudflare Registrar .com | $9.15/年 | ≈ ¥5.5 |
| **合计** | | | **≈ ¥225/月** |

**R2 的零出流量费是图片类应用的杀手锏。** 对比：同样 10 TB 出流量，R2 收 $0，GCP 收 $1,137。
本方案 34 GB/月的图片流量完全免费，只剩存储费。

⚠️ 缺点：服务器在境外，国内访问有 100~200ms 延迟且不稳定；**不需要备案**。

### 方案 C：国内服务器 + R2（❌ 不推荐）

R2 在大陆没有节点，国内用户加载图片会很慢。要么国内全套，要么海外全套，别混搭。

### 服务器规格说明

**为什么是 4核8G 而不是 2核4G？**

- API 请求本身很轻（100 并发对 Node.js 毫无压力）
- 真正的内存/CPU 消耗在 **sharp 处理上传图片**：一张 20MB 的图解码后在内存里可能占 200MB+
- 4核8G 能从容应对 5~10 人同时上传；2核4G 在峰值时有 OOM 风险

## 四、X API vs 手动上传：到底省多少

### 4.1 决定性前提：谁来承担采集范围？

这一条直接决定成本差 1000 倍以上：

| 模式 | 说明 | 月成本 |
| --- | --- | --- |
| **每人各自抓** | 1000 个用户 × 各自 500 个关注者 × 100 条 | **$250,000** ❌ |
| **全站共享采集** | 统一抓 200 个公共账号，大家共用 | $150 |
| **手动上传** | 用户自己存图自己传 | **$0** |
| **BYOK** | 用户填自己的 API Key，抓自己的关注者，费用记在他账上 | **$0（你承担）** |

「每人各自抓」= 5000 万条 × $0.005 = $250,000/月，**完全不可行，连讨论的必要都没有**。
这一条必须先跟你确认清楚。

### 4.2 手动上传相对 API 节省的金额

| 对比基准 | 每月节省 |
| --- | --- |
| vs 全站共享采集（200 账号日增） | **$150/月（≈ ¥1,080）** |
| vs 每人各自抓取 | **$250,000/月** |
| vs BYOK | $0（BYOK 本来就不花钱） |

**即：手动上传相比最现实可行的 API 方案，每月省约 ¥1,080 —— 是基础设施成本的 4 倍多。**

### 4.3 手动上传的隐藏成本

不是钱，是**用户时间**。按每张图 30 秒（打开推特 → 保存图片 → 上传）计，
用户每月收集 200 张 ≈ 100 分钟。这笔成本由用户自愿承担，但摩擦太大用户会流失。

### 4.4 推荐方案：把手动上传的摩擦降到最低 + BYOK 兜底

**手动上传三件套（建议实现，成本几乎为零）：**

1. **Ctrl+V 粘贴** —— 在推特上右键「复制图片」，回到网站直接粘贴，省掉"保存文件"这一步
2. **批量拖拽** —— 一次拖 20 张进页面
3. **粘贴图片 URL** —— 复制 `pbs.twimg.com/...` 链接，粘贴后由服务器下载。
   这是摩擦最小的路径：不用下载、不用选文件、**且完全不走 X API，零成本**

**BYOK（用户自带 Key）：**

- 用户在设置页填自己的 X API Bearer Token（**加密存储**）
- 服务器用该 Token 抓他自己的关注者，费用记在他自己的 X 开发者账号
- 你一分钱不花，每个用户抓到的还是自己真正关心的内容
- 需要配套：Token 加密、每用户抓取配额、可随时停用

**这套组合拳下来：你的 API 成本 = 0，基础设施 = ¥250/月。**

## 五、100 人并发的技术评估

### 5.1 SQLite 撑得住吗？—— 撑得住

- WAL 模式下**读并发无锁**，写操作串行但单次事务 < 1ms，理论数千写/秒
- 100 人同时保存标注（每人几十条记录）远未触及上限
- **已修复一个真实隐患**：原先未设置 `busy_timeout`，并发写入会直接抛 `SQLITE_BUSY`。
  现已设为 5000ms 排队等待（见 `src/lib/db.ts`）

### 5.2 真正的瓶颈与对策

| 瓶颈 | 影响 | 对策 |
| --- | --- | --- |
| **图片 I/O 与带宽** | 服务器带宽被图片吃满，页面卡死 | 图片卸载到对象存储 + CDN |
| **sharp 内存** | 多人同时上传大图 → OOM 崩溃 | **已加并发限流**（同时最多 2 张）+ 单批 20 张上限 |
| **单实例无冗余** | 进程崩溃/重启 = 服务中断 | PM2 或 systemd 守护 + 数据库定时备份 |
| **磁盘容量** | 图片增长超出系统盘 | 云硬盘 ¥1/GB/月，或直接上对象存储 |

### 5.3 上对象存储前，本地磁盘方案的上限

- 单实例、图片走本地磁盘时，**128 GB（重度档）仍可放在 180 GB 系统盘内**
- 但**无法水平扩展**（多实例看不到彼此的磁盘）
- 一旦要加第二台机器，就必须换成对象存储 —— 改造点已在 `src/lib/storage.ts` 隔离好

## 六、本次已实施的成本/稳定性优化

1. **SQLite 并发写等待**（`busy_timeout = 5000` + `synchronous = NORMAL`）
   —— 多人同时保存标注不再报错
2. **图片统一转 WebP + 最长边 1800**
   —— 存储与流量直接降 50~60%，是本次最大的成本优化
3. **sharp 并发限流 + 单批上传上限**
   —— 防止多人同时上传导致进程 OOM

### 协作模型（已实现）

| 角色 | 能做 | 不能做 |
| --- | --- | --- |
| 所有者 | 全部操作：内容增删改、成员管理、改空间信息、删除空间 | —— |
| 可编辑 | 空间内图片与标注的增删改 | 成员管理、空间设置、删除空间 |
| 只读 | 查看、**导出** | 任何写操作（接口返回 403） |

- 空间可见性：`private`（仅成员）/ `public`（登录用户可见，非成员只读）
- 空间创建者不可被移除或降级
- 无访问权时接口返回 **404**（不泄露空间是否存在），权限不足返回 **403**

### 为什么额外做了「共享图库」

原本素材是每人私有的。测试时发现：协作成员只能添加**自己**图库里的图，
看不到别人上传的素材 —— 这样「协作」和「全站共享」都落不了地。

因此加了 `assets.visibility`：

- 上传 / 链接导入时可勾选「共享到公共图库」
- 共享素材对其他登录用户可见，可加进自己的空间去标注
- 他人共享的素材**只能使用，不能重命名或删除**（接口层按 owner 隔离）
- 未来全站共享采集的图片直接写入 `visibility='shared'`，天然成为公共图库

### 手动上传的三种入口（零 API 成本）

| 方式 | 操作 | 摩擦 |
| --- | --- | --- |
| 上传文件 | 点击 / 拖拽 / `Ctrl+V` 粘贴剪贴板 | 低 |
| **图片链接导入** | 复制 `pbs.twimg.com` 直链 → 粘贴 | **最低**（不用下载、不用选文件） |
| 共享图库 | 直接取用他人共享的素材 | 零 |

链接导入带完整 SSRF 防护：拦截内网地址与非常规协议，限制大小、类型与重定向跳数。

建议先用手动上传 + 链接导入跑一段时间，看真实用户的素材供给速度再决定。
