### 3. 注册限流重做 ✅
原来：进程内存 `Map` + `x-forwarded-for` 无条件采信。两个问题：
- dev 模块重载 / 多进程部署 → 计数清零或各算各的
- **XFF 可伪造 → 攻击者换个头就换一个桶，限流形同虚设**（这是最严重的）

现在 `src/lib/register-guard.ts` + `db.ts`：
- 计数落 **SQLite `rate_limits` 表**（固定窗口，`db.transaction` 保证原子），多进程/重启都不丢
- `TRUST_PROXY=1` 才采信反代头，否则落 `unknown` 桶
- **IP 桶（默认 3/小时，`REGISTER_MAX_PER_IP`）+ 全局桶（默认 30/小时，`REGISTER_MAX_GLOBAL`）双闸门**，全局桶兜住"伪造 IP 轮换"
- 429 响应带真实的 `Retry-After`
- 每次调用 1% 概率清理 24h 前的过期桶

**验证**：3 次 200 → 第 4、5 次 429；伪造 `X-Forwarded-For: 99.99.99.1/2/3` 仍 429；`rate_limits` 表里 `register:ip:unknown=3`、`register:global=3`；`retry-after: 3580`。
（顺带：登录失败限流现在只需 3 行 `consumeRateLimit('login:fail:'+ip, 5)`，你要就说一声。）

### 4. 嵌字撤销覆盖文字层 ✅
`TypesetEditor.tsx` 撤销栈从「只存涂改层 Blob」改成 **快照 = 涂改层位图 + 文字层列表 + 选中项**：
- 新增文字层、删除文字层、改文字、改字号、从标号生成、涂改、自动去字 → 全部可撤销
- **重做**（Ctrl+Shift+Z / Ctrl+Y / 按钮）一并加上
- 第 0 步基线 = 刚加载的草稿：第一次撤销回到磁盘草稿，而不是把草稿整层擦掉（旧实现会）
- 文字连续输入做了 700ms 合并，不会一个字吃掉一步（50 步上限才够用）
- 撤回到"已保存"的那一步时，保存草稿按钮自动变回不可用（脏标记跟着历史走）

**验证**：从标号生成 3→7 层，撤销→3（且"未保存"消失），重做→7，撤销→3；文字工具加层 3→4→撤销→3；删层 4→3→撤销→4；改文字"译文"→"UNDO_TEST_TEXT"→撤销→"译文"；画笔 ink 0→19→撤销→0。

### 附带修复：LabelPlus 导出格式兼容性（对应你的第 7 条）
对照官方格式（`MomoLabelPlus` 的 `lp_head`、`labelplus_web` 的生成器，两者一致）：
```
1,0
-
框内
框外
-
Default Comment
You can edit me
（空行）
（空行）
>>>>>>>>[文件名]<<<<<<<<
----------------[1]----------------[0.456,0.210,1]
译文
```
我们原来导出**缺 "Default Comment" 的正文行和空行**，严格解析器会把第一个 `>>>>>>>>[文件]<<<<<<<<` 当成注释正文吃掉 → **首个文件的标号全部丢失**。已补上（`src/lib/labelplus.ts`）。

## 四、多人实时协作 + 服务器负载（对应你的第 5 条）

**先说结论：你要的"标注/标号/文字层"实时协作，一台 2核4G 的轻量云服务器完全扛得住；真正扛不住的是"涂改层像素"的实时同步。**

### 负载测算（按 2C4G / 5Mbps 带宽）
| 数据类型 | 单次大小 | 频率 | 10 人同时编辑一张图 |
| --- | --- | --- | --- |
| 标注/标号/文字层 JSON | 0.1~5KB | 每次操作 | ~10KB/s，**毫无压力** |
| WebSocket 空闲心跳 | 2B | 25s/次 | 可忽略 |
| SQLite 写入 | - | 每次保存 | WAL + busy_timeout=5000 已配好，10 人并发够用 |
| **涂改层像素（paint.png）** | 200KB+ | 每一笔 | 5Mbps=625KB/s，**3 人全量广播就打满** |

### 分级落地方案（强烈建议按 L1 → L2 走，不要直接上 L3）
- **L0（现状）**：HTTP 全量保存，无实时。不同人编辑不同图没问题，同一张图会互相覆盖（后保存的赢）。
- **L1 编辑锁（1~2 天，推荐先做）**：
  - `editing_locks(item_id, user_id, expires_at)` 表；打开编辑器即加锁，30s 心跳续约，关页/超时自动释放
  - 其他人进入同一张图 → **只读** + 顶部提示"XX 正在编辑中"
  - 保存时校验锁持有者，非持有人 409
  - 不需要 WebSocket，10s 轮询一次锁状态就够 —— 这正是你说的"加锁方案"，成本低、收益立竿见影
- **L2 实时只读镜像（3~5 天）**：SSE/WebSocket 把"别人的标注/文字层变更"推给同房间的人看；写仍走 L1 锁。满足"能看到别人改到哪了"
- **L3 真·多人同时编辑（1~2 周）**：Yjs + y-websocket（内存占用极小，一台 2C4G 能挂几千房间），持久化回 SQLite。**只有在 L1/L2 不够用、且确定要"两人同时画框"时才上**

**注意**：涂改层（P图）无论哪一级都建议**独占编辑**（进 L1 锁），不要做像素实时同步——收益低、带宽炸。要共享涂改结果，保存后推一张缩略图即可。

### 服务器规格建议
- 2C4G：标注/文字层实时 + 50 人在线没问题
- 4C8G：可以加 OCR/LaMa sidecar（你已有 RTX 3080 方案，GPU 推理别和 Web 同机抢内存）
- 前置 Nginx 记得配 `proxy_set_header X-Forwarded-For` + 应用侧 `TRUST_PROXY=1`，否则限流的 IP 桶失效

## 五、开放公共空间改造方案（对应你的第 8 条）

你要的模型：**没有私人图库/私人空间，全站一个开放区，公共文件夹大家自由增删改查，改动实时共享；做不到实时就加锁。**

### 需要动的数据模型
| 现状 | 改成 |
| --- | --- |
| `assets.visibility` = private/shared，靠勾选"共享到公共图库" | **字段保留但默认 shared，UI 去掉勾选**（上传即公共）。最省事的路线 |
| `spaces.visibility` = private/public | 去掉 private，全部公开 |
| `space_members` 三级权限（owner/editor/viewer） | 所有人默认 editor；只保留"创建者/管理员"能删文件夹和清空内容 |
| 图库"我的/共享"两个 Tab | 合并成一个公共图库 + 搜索 |
| 个人删除权 | 公共内容任何人可删（你说的"自由增删改查"），但要加**操作日志**（谁删的）+ 可选的软删除/回收站，否则会被人清空 |

### 实时共享怎么接（结合第四节）
- **标注/标号/文字层**：L2 实时镜像（SSE 推送）即可满足"公共文件夹里的图片被修改时实时共享"
- **嵌字涂改层**：走 L1 编辑锁 —— 被编辑中的图片其他人只读，看的是保存前的状态，保存后刷新可见
- 这正好是你第 8 条里说的两套方案的组合：**文本类实时共享 + 像素类加锁**

### 建议的实施顺序
1. **第一步（半天）**：`assets.visibility` 与 `spaces.visibility` 默认公开 + 去掉相关 UI 开关（保留字段，可回滚）
2. **第二步（半天）**：图库合并"我的/共享"Tab；空间列表去掉"新建私人空间"
3. **第三步（1~2 天）**：L1 编辑锁（含嵌字页）
4. **第四步（3~5 天）**：L2 实时镜像（标注 + 文字层）
5. **第五步（可选）**：Konva 重构文字层（第三节的建议）

⚠️ **需要你确认的一个点**：去掉私人空间 = 现有的 `space_members` 权限模型基本作废，所有登录用户对所有文件夹都有编辑权。如果你还想要"某些文件夹只给 certain 人"，就得保留一层"文件夹成员"概念，只是不再有"私人空间"。**你定：完全开放（我按 1-4 直接做）还是保留文件夹级可见性？**
